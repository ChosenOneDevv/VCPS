## Gate 5 — Security

**Touched categories (risk-model.md D2/D3/D4 via critical_domains
financial-ledger / tenant-isolation / external-payment-callbacks):**
`VCPS-G5-002`-adjacent credential verification (webhook signature, not
login), `VCPS-G5-003` (object-level access control), `VCPS-G5-011`
(external provider/webhook trust and idempotency).

**Independent (`I2`) findings, same fresh session as Gate 4:**
- `VCPS-G5-011` webhook authenticity: `hmac.compare_digest` constant-time
  signature check -- confirmed, not vulnerable to a timing attack.
- `VCPS-G5-003` object-level check: payload identity (`tenant_id`/
  `order_id`/`event_id`) is bound to the caller's actual arguments, not
  merely "a signature exists" -- confirmed, this is exactly what makes
  the forged-cross-tenant test pass.
- `VCPS-G5-011` idempotency (money-relevant, D2): a replayed identical
  event cannot re-settle -- confirmed via the `event_id`/`status` guard
  under `store.lock`.
- `VCPS-G5-005` server-side enforcement: all checks are server-side in
  `settle_payment` itself; no client-side-only control exists here.
- No injection class (`VCPS-G5-010`) applies -- no query/command/path is
  constructed from this input. No file upload (`VCPS-G5-009`) or
  privilege escalation (`VCPS-G5-004`) path exists in this function.

Per `VCPS-G5-012`, this project's money-relevant exposure (`D2` rated `3`)
is `HIGH`+ severity, so these categories require executed (`E2`+)
evidence, not static review alone -- satisfied, via the real, independent
test re-run above.

**Why this still cannot `PASS` or `PARTIAL`:** the same evidence-tier gap
as Gate 4 applies identically here -- `VCPS-G5-014` cross-references the
same baseline mechanism `VCPS-G4-002`/`VCPS-G3-009` use, and
`levels.md §5`'s `L3` `HIGH`-severity blocking threshold is not
gate-specific. `FND-5ed8b1b2-2b5a-41f0-8df1-94287d034ec2` (`HIGH`, `OPEN`,
no `HC-08`) blocks this gate for the identical reason as Gate 4.

`BLOCKED` (`EVIDENCE`/`DECISION`, same basis as `GATE-718c3ad0`). Every
security category this change actually touches was substantively
evaluated at `I2` independence with no defect found; the block is the
project's standing no-CI gap, not a security defect in `settle_payment`.
